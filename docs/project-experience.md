## 2. 대표 사례 A — 공사 원가 산정 업무 시스템화 및 재산정 기능

**연결 프로젝트:** kt P&M 구매 및 공사 자재 시스템(2025.12~현재)  
**역할:** PM·PL과 기존 업무/엑셀 분석, 현업 요구사항 협의, 전체 TO-BE 설계를 공동 수행. 프론트엔드·백엔드·원가 계산 로직 직접 개발. 현업 테스트 및 계산 결과 검증 참여. **재산정 기능은 요구사항 분석·로직 설계·개발 직접 수행.**

### AS-IS / 과제

- 공정내역서 작성 전 담당자가 자재별 단가와 일위대가를 엑셀에서 직접 갱신해야 했음.
- 담당자별 엑셀 양식과 산정 기준·계산식이 달라 자료 취합, 결과 비교, 계산 근거 확인에 추가 작업이 필요했음.
- 자재 단가·구성·수량 등 기초 데이터는 산정 이후에도 변경되므로, 변경된 부분을 업무 상태에 맞게 반영할 필요가 있었음.

### TO-BE / 실제 구현

1. **기초 원가정보 관리**: 외부 시스템 자동 연계와 관리자 수동 관리를 병행. 관리 구분 코드값으로 두 대상을 구분.
2. **수정 권한 제어**: 자동 연계 데이터는 화면에서 수정을 제한하고, 백엔드 Service에서 DB의 관리 구분 코드를 확인해 수정 요청을 차단. 수동 관리 대상만 화면 수정 허용.
3. **산식 표준화**: 담당자별 엑셀 계산 기준을 분석해 공통 산식 + 조건별 예외 산식 구조로 구현. 산식 종류와 적용 조건을 DB 테이블에서 관리하고 해당 계산 로직을 실행. 이미 구현된 산식의 적용 조건은 DB 데이터 수정만으로 변경 가능(새 계산식 자체의 무배포 추가 가능 여부는 미확인).
4. **변경 감지·추적**: 변경 플래그로 변경 자재를 식별하고 관련 품목을 조회. 별도 변경 이력 테이블로 변경 내역 추적.
5. **재산정 대상 표시**: 기초 데이터가 바뀌어도 기존 작성 문서를 자동 덮어쓰지 않음. 영향을 받은 품목을 화면에 표시하고 사용자가 선택한 경우에만 재산정.
6. **부분 재산정**: 변경 플래그로 대상 항목을 구분해 변경된 기초정보 관련 항목만 갱신하고, 변경되지 않은 작성 데이터는 유지.
7. **상태별 제어**: `공정내역서 작성 중` / `원가계산서 작성 중`은 재산정 가능, `원가계산서 확정`은 변경·재산정 대상에서 제외.
8. **확정 데이터 보존과 재사용**: 확정된 원가계산서의 기존 결과는 유지. 확정 내역을 기반으로 새로운 공정내역서를 생성할 때는 **최신 마스터의 자재 구성·수량·단가**를 적용.
9. **검토·승인**: 검토 요청, 승인·반려, 상태별 수정·삭제 제한, 승인·반려 이력 관리.
10. **전자결재 연계**: 외부 전자결재 시스템에 결재 요청을 송신하고, 외부 시스템의 Callback API로 승인·반려 결과를 수신해 원가계산서 업무 상태에 반영. 별도의 Callback 중복 수신 방지 로직은 구현하지 않았으므로 면접에서 멱등성 보장 사례로 주장하지 말 것.

### 실제 개선 효과

- 공정내역서 작성 전 자재 단가·일위대가를 개별적으로 갱신하던 엑셀 수작업 감소.
- 원가 산정 기준의 공통화와 조건별 예외 규칙 관리.
- 계산 근거 및 변경 이력 조회 편의성 개선.
- 검토·승인 진행 상태를 시스템에서 관리.
- 확정 결과 보존과 작성 중 문서의 부분 재산정을 함께 지원.

**성과 유의:** 업무 시간 단축률이나 오류 감소율은 측정치가 없으므로 기재하지 않음.

### 자기소개서에 활용할 수 있는 핵심 문장

> 공정내역서를 작성하기 전 담당자가 개별 엑셀 파일에서 단가와 일위대가를 갱신하던 업무를 분석하고, PM·PL과 공통 업무 흐름을 정의해 시스템으로 전환했습니다. 저는 화면·백엔드·계산 로직을 개발했으며, 특히 기초정보 변경 이력과 업무 상태를 고려한 재산정 기능을 요구사항 분석부터 구현까지 직접 담당했습니다.

## 3. 대표 사례 B — 인터페이스 성능 개선 2건

**연결 프로젝트:** HD현대 HI-SRM 구축(2023.06~2024.01)

### 사례 B-1. 건별 호출을 다건 분할 전송으로 개선

- **기존 문제:** 데이터 건수만큼 인터페이스를 개별 호출하여 대량 데이터 전송 시 호출 횟수와 처리 시간이 증가.
- **개선:** 팀과 개선 방향을 공동 검토·결정하고, 다건 전송용 신규 인터페이스의 **송신 측**을 직접 개발. 전송 데이터를 일정 건수 단위로 나눠 호출하여 성능과 안정성을 함께 고려.
- **결과:** 호출 횟수가 감소하고 대량 데이터 처리 속도가 크게 향상됨을 확인. 정확한 전후 측정치는 기억나지 않아 수치화하지 않음.
- **역할 구분:** 수신 측 개발까지 담당했다고 주장하지 않음. 개선안은 팀과 공동 결정.

### 사례 B-2. 데이터 전처리와 조회 재사용을 통한 연계 최적화

- **기존 문제:** 시스템 A에서 가져온 데이터를 기반으로 시스템 B를 반복 호출해 최종 데이터를 구성. 중복 데이터와 불필요한 조회 대상 때문에 반복 호출 발생.
- **개선:** 문제를 직접 발견하고 개선 방안을 제안·구현. A의 조회 결과를 전처리해 **중복 제거, 불필요한 데이터 필터링, 기존 조회 결과 재사용, 필요 데이터 일괄 호출, 응답과 원본 데이터 매핑** 수행.
- **결과:** A 조회부터 B 연계 및 최종 데이터 완성까지 **약 15초 → 약 1초(약 93% 감소)**. 정확한 측정 기록이 아닌 기억에 따른 대략적인 수치.
- **역할:** 문제 발견, 개선안 제안, 구현을 직접 수행.

### 자기소개서에 활용할 수 있는 핵심 문장

> 시스템 연계 과정에서 중복 데이터로 인해 동일 인터페이스가 반복 호출되는 문제를 발견했습니다. 조회 결과 재사용과 중복 제거·필터링을 적용하고 필요한 데이터를 일괄 요청하도록 구조를 변경해 전체 처리 시간을 약 15초에서 1초 수준으로 줄였습니다.

## 4. 대표 사례 C — SQL 목록 조회 최적화

**연결 프로젝트:** kt P&M 구매 및 공사 자재 시스템

- **상황:** 공정내역서·원가계산서 목록에서 일위대가, 품목, 단가의 변경 여부까지 표시해야 해서 여러 상세 테이블을 조인. 목록 조회가 느려짐.
- **분석:** SQL 실행계획을 확인해 비효율적인 조인 및 데이터 접근 구조 검토.
- **조치:** 변경 여부만 판단하는 부분은 `JOIN`을 `EXISTS`로 변경; 먼저 조회 조건으로 대상을 축소; 서브쿼리·집계 구조 조정; 조회/조인 조건에 맞게 인덱스 사용을 고려해 SQL과 인덱스 개선.
- **결과:** 약 **10,000건** 기준, **검색 버튼 클릭부터 목록 화면 표시까지** 약 **10초 → 2초(약 80% 감소, 약 5배 빠름)**.
- **유의:** 기억에 따른 대략적인 수치. 순수 DB SQL 실행 시간이 아닌 **화면 전체 목록 조회 시간**임을 명시할 것.

### 자기소개서에 활용할 수 있는 핵심 문장

> 공정내역서·원가계산서 목록에서 여러 테이블의 변경 여부를 함께 조회하면서 발생한 병목을 실행계획으로 분석했습니다. 존재 여부만 필요한 조인을 `EXISTS`로 바꾸고 조회 대상·집계 구조·인덱스 사용을 개선해, 약 1만 건 조회 시 화면 표시 시간을 10초에서 2초 수준으로 단축했습니다.

## 5. 대표 사례 D — WAS 환경 차이에 따른 엑셀 생성 장애 해결

**연결 프로젝트:** kt P&M 구매 및 공사 자재 시스템  
**역할:** 장애 분석, 원인 발견, WAS 설정 변경, 정상화 검증까지 직접 수행.

- **증상:** 동일 애플리케이션을 실행하는 두 WAS 중 특정 서버에서 생성한 엑셀(XLSX) 파일만 손상되어 정상적으로 열리지 않음.
- **분석:** OS·JDK·Tomcat 버전과 환경을 비교하고, `shared.loader` 설정과 라이브러리 참조 구조의 차이 발견. 생성된 XLSX 내부 XML 구조 차이와 XML 처리 라이브러리 로딩 영향을 조사.
- **해결:** 문제가 발생한 WAS의 `shared.loader` 설정 제거/비활성화 후 정상 동작 확인.
- **결과:** 애플리케이션 소스 변경 없이 서버 설정 조정으로 엑셀 생성 장애 해결.
- **정확성 주의:** `shared.loader` 설정 차이는 정상화로 확인했지만, 특정 라이브러리 충돌의 정확한 내부 메커니즘까지 확정한 것으로 표현하지 않음.

### 자기소개서에 활용할 수 있는 핵심 문장

> 동일한 소스와 실행 환경인데 특정 WAS에서만 엑셀 파일이 손상되는 장애가 발생했습니다. 두 서버의 설정 및 라이브러리 참조 경로를 비교해 Tomcat `shared.loader` 설정 차이를 확인했고, 해당 설정을 비활성화해 애플리케이션 소스 변경 없이 장애를 해결했습니다.
